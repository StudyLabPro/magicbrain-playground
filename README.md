# MagicBrain Playground

Рабочий стенд библиотеки [MagicBrain](https://github.com/StudyLabPro/MagicBrain):
сеть действительно обучается, нейрогенез действительно прогоняется по стадиям,
повреждение действительно наносится, а сравнение с ACT-бэкендом
[Balansis](https://github.com/StudyLabPro/Balansis) действительно измеряется.
Заглушек и заранее записанных чисел здесь нет — всё, что показано в интерфейсе,
посчитано в момент запуска и сохранено в файл прогона.

Всё работает на CPU. GPU для этого не нужен и не был бы использован: ядро
MagicBrain — numpy/float32, ни одной операции на CUDA в нём нет (единственный
GPU-код в библиотеке — обёртки чужих torch-моделей).

---

## Что здесь можно сделать

| Сценарий | Что делает | Что показывает |
|---|---|---|
| **Обучение** | обучает `TextBrain` на выбранном тексте | кривую обучения, состояние субстрата и качество на **отложенном хвосте** против трёх опорных моделей |
| **Нейрогенез** | компиляция генома → морфогенез → обучение → воспроизведение → оценка | пять стадий по отдельности: время, метрики, геном, ткань, верность воспроизведения, аттракторы |
| **Самовосстановление** | обнуляет долю весов — рекуррентных, readout или обоих — и дообучает | насколько глубока просадка и какая её доля отыгрывается |
| **ACT / Balansis** | один геном и один seed, две арифметики | качество, скорость и численный дрейф, плюс микробенчмарк, где компенсация реально решает |
| **Прогоны** | список сохранённых прогонов | любой можно открыть заново, выгрузить JSON, взять как основу для повреждения |

Модель, обученную в стенде, можно одной кнопкой отдать в соседний контейнер со
штатным `MagicBrain API` и сгенерировать текст уже его рантаймом — это проверка,
что артефакт настоящий, а не внутренний объект стенда.

### Честная оценка вместо «loss упал»

Обучающий loss сам по себе не значит ничего: сеть может просто запомнить строку.
Поэтому каждый прогон режет текст, держит хвост в стороне от обучения и считает
на нём три опорные модели — равномерную, униграммную и биграммную. Вердикт
формулируется в этих терминах: **бьёт ли сеть униграмму и биграмму**.

Результат честный, и он не в пользу заявленных возможностей: на посимвольных
задачах `TextBrain` уверенно обгоняет униграмму, но **биграммную модель не
догоняет** ни на английском Шекспире, ни на синтетике с известной энтропией
источника. На 100 000 шагов: Шекспир — 4.67 бит/символ против 4.79 у униграммы
и 3.44 у биграммы; синтетика — 2.998 против 4.12 и 1.64 при скорости энтропии
самого источника 1.15. Все числа и условия — в [`docs/RUNS.md`](docs/RUNS.md);
масштаб везде один, 100 000 шагов обучения, и `make smoke` прогоняет ровно его.

Ещё три результата того же прогона, которые стоит знать заранее:

- **обнуление до 40% рекуррентных синапсов почти не меняет предсказание**
  (4.666 → 4.641 бит/символ), а повреждение линейного readout — меняет
  (4.666 → 4.844) и отыгрывается дообучением примерно наполовину. Работу делает
  readout, а не рекуррентная динамика;
- **ACT-бэкенд Balansis медленнее в 3.09× и не меняет качество** (разница
  0.00045 нат/символ). В микробенчмарке на плохо обусловленных данных его ошибка
  ровно ноль против `math.fsum`, тогда как у numpy 5.7e-06 — то есть ACT
  работает как заявлено, просто эта задача его не требует;
- **поиск аттракторов даёт один аттрактор**, в который сходятся все пробы, и
  почти все нейроны в нём активны. Это коллапс динамики, а не аттракторная
  память.

## Быстрый старт

```bash
cp .env.example .env    # порты и лимиты по умолчанию — на loopback
make corpora            # корпуса уже в репозитории; шаг нужен для пересборки
make build              # prepare выполняется сам: снимок исходников фиксированной ревизии
make up                 # каталоги состояния make готовит сам
make status
```

`make build` требует локальный клон MagicBrain (путь задаётся в `.env`); `make up`
работает с уже собранным образом и репозиторий библиотеки не трогает. Образ при
запуске не пересобирается и тег не меняется: разворачивается ровно то, что
собрали и проверили.

Интерфейс: `http://127.0.0.1:8007/`. Последовательность с проверками и откатом —
в [`docs/DEPLOY.md`](docs/DEPLOY.md).

Прогнать все сценарии разом и получить сводку:

```bash
make smoke       # 100 000 шагов на сценарий; пишет var/scenarios-summary.json
make runs-doc    # пересобирает docs/RUNS.md из файлов прогонов
```

`make smoke` в конце перечитывает каждый прогон через HTTP и сравнивает
сериализованный JSON целиком, а не одно число одного прогона.

## Как это устроено

Два контейнера из одного образа:

- **`mb-playground`** (`127.0.0.1:8007`) — FastAPI и однофайловый интерфейс без
  сборки; очередь задач в пуле потоков; прогоны в JSON на диске.
- **`mb-api`** (`127.0.0.1:8008`) — штатный `api/` из репозитория MagicBrain, без
  единой правки. Каталог моделей у контейнеров общий, поэтому обученная модель
  видна обоим.

Один образ на оба — чтобы библиотека была гарантированно одной ревизии и модель,
записанная стендом, читалась рантаймом без сюрпризов. Ревизия зашита в образ:
`scripts/prepare_build.sh` берёт `git archive HEAD`, а не рабочее дерево, и
записывает SHA — он виден в шапке интерфейса и в каждом прогоне.

Стек живёт в собственной изолированной сети. Это важнее, чем кажется: у `mb-api`
нет никакой авторизации, поэтому он не должен оказаться в сети, где его видят
посторонние контейнеры, — оттуда были бы доступны и удаление моделей, и запуск
обучения. Внешний маршрут вынесен в отдельный файл `docker-compose.publish.yml`,
который подключается только при `MBP_TRAEFIK_ENABLE=true`, и `mb-api` наружу не
попадает никогда.

Обе службы работают с файловой системой только на чтение, без новых привилегий и
без capabilities; писать можно в `/data` (это `./var`) и в `tmpfs` на 64 MB.
Имена контейнеров, сети и объектов Traefik берут префикс из `MBP_NAME`, поэтому
второй экземпляр поднимается без правки compose-файлов.

Ресурсы ограничены в `deploy.resources.limits` (по умолчанию 4 vCPU и 6 GB на оба
контейнера) плюс потолок в 256 процессов на контейнер. Прогонов на диске — не
больше `MBP_MAX_RUNS`: при сохранении нового самые старые удаляются вместе с
моделями.

## Данные

Используются только тексты, происхождение которых можно назвать: общественное
достояние (D0), собственные материалы экосистемы (D1) и синтетика, порождённая
скриптом (D2). Класс данных виден рядом с каждым корпусом и записывается в каждый
прогон вместе с sha256 фактически использованного куска текста. Состав, основания
и расчёт энтропии синтетического источника — в [`docs/DATA.md`](docs/DATA.md).

Продуктовые данные и телеметрия пользователей здесь не используются и
использоваться не могут — это запрет уровня экосистемы, а не настройка стенда.

## Границы: что здесь работает, а чего в MagicBrain нет

Это важнее списка возможностей.

**Работает и проверено прогоном:**

- обучение `TextBrain` (дофамин-модулированный Хебб плюс градиент по линейному
  readout), сохранение и перезагрузка модели;
- компиляция генома из статистики текста, морфогенез с CPPN, созревание порогов,
  авторегрессивное воспроизведение, поиск аттракторов;
- обнуление доли синапсов и дообучение после него;
- компенсированная арифметика Balansis на пути обучения.

**Не существует в коде, вопреки тому, как это иногда звучит в документах:**

- **роста сети во время обучения нет.** Число нейронов `N` задаётся геномом один
  раз; «нейрогенез» — это компиляция генома и морфогенез *до* обучения. Во время
  обучения меняются только рёбра: `prune`/`rewire` при неизменном `N`;
- **сжатия данных нет.** Есть метрика `genome_ratio = длина генома / размер
  данных` и отдельно измеряемая верность воспроизведения, которая далеко не
  единица. Обратного преобразования с гарантией не существует, поэтому сравнивать
  это число с gzip некорректно — стенд показывает строки gzip/bz2/lzma рядом
  именно как напоминание об этом, а не как победу;
- **`damage_edges` не удаляет рёбра**, а обнуляет их веса: структура графа после
  «повреждения» та же, восстановление идёт по уже существующим связям. Хуже того,
  прогон показал, что обнуление до 40% рекуррентных синапсов почти не меняет
  качество предсказания — работу несёт линейный readout, которого штатное
  повреждение не касается. Поэтому здесь добавлен выбор цели повреждения
  (`recurrent` / `readout` / `both`): без него «бенчмарк самовосстановления»
  измеряет устойчивость к удалению того, что и так почти не влияет на ответ;
- **distributed training и production inference server** из README MagicBrain не
  сделаны — в roadmap это незакрытые чекбоксы;
- **цифровых двойников тут нет вовсе.** Класс `NeuralDigitalTwin` в библиотеке
  есть, но его mastery меняется эвристическими приращениями, состояние сети в
  расчёт не входит, а живого потока данных к нему не существует. Показывать это
  как работающую функцию было бы неправдой, поэтому сценария с двойниками в
  стенде нет;
- **GPU не используется.** См. ниже.

## Что было починено в MagicBrain по ходу работы

Стенд писался не как витрина, а как способ проверить библиотеку прогоном. Три
дефекта нашлись именно так.

1. **Аксональные задержки схлопывались в один буфер (P0)** — коммит `1b80631`.
   `forward` сдвигал линию задержек перепривязкой элементов списка, а не
   переносом значений; после четырёх шагов все пять буферов задержек указывали на
   один массив. Механизм, вынесенный в заголовок модуля как ключевая особенность
   архитектуры, переставал работать почти сразу после старта обучения.
2. **Сохранение модели теряло обученную топологию (P1)** — тот же коммит.
   `save_model` писал только веса, `load_model` пересобирал граф из генома, а
   структурная пластичность к этому моменту уже переставила рёбра. Веса одной
   сети ложились на рёбра другой, тихо и правдоподобно.
3. **`model_id` из запроса подставлялся в путь файла без проверки (P1)** — коммит
   `ccf25d6`. `../../etc/passwd-probe` уводил запись за пределы каталога моделей;
   на живом сервисе запись дошла до файловой системы и остановилась только на
   правах пользователя. Теперь идентификатор проверяется в маршрутах и повторно в
   `RuntimeService.model_path`; тот же зонд возвращает `422`.

Все три закрыты регрессионными тестами, которые падают на предыдущих коммитах:
`tests/test_delay_line.py`, `tests/test_io_topology_roundtrip.py`,
`tests/test_model_id_validation.py`. Полный набор библиотеки — **423 passed,
1 skipped** (пропущен `tests/integration/test_magic_wiring.py`, которому нужен
отсутствующий `studyninja_magic`).

Отдельный результат, который стоит знать: **исправление задержек не улучшило
предсказание** — разница между «до» и «после» лежит внутри разброса по seed.
Иначе говоря, заявленный механизм аксональных задержек на этой задаче ничего не
даёт. Измерение — в [`docs/RUNS.md`](docs/RUNS.md).

## Чего здесь нет и что появится с GPU

GPU-версии у MagicBrain нет ни в каком виде: `TextBrain` — numpy/float32,
JAX-бэкенд объявлен, но ядром не используется, `torch_backend` упомянут, а файла
нет; компенсированные операции Balansis существуют только как numpy float64 на
CPU. Поэтому на текущих размерах (`N` = 1024–1216, `K` = 12–20) GPU не дал бы
ничего: шаг обучения занимает доли миллисекунды.

Отложено до появления GPU:

- **гибриды SNN↔DNN/Transformer** — код композиции есть, torch-адаптеры есть, но
  осмысленный прогон требует видеокарты под DNN-часть;
- **батчирование популяций геномов** — единственная нагрузка MagicBrain, где GPU
  был бы оправдан; для этого нужен `torch_backend` для `TextBrain`, которого не
  существует;
- **компенсированная арифметика на устройстве** — ни в MagicBrain, ни в Balansis
  её нет; без неё «обучение на GPU с ACT» остаётся планом, а не фактом.

## Состав репозитория

```
mbplay/                 сервис стенда
  app.py                HTTP-слой
  jobs.py               очередь задач
  store.py              прогоны на диске
  corpora.py            реестр корпусов с классами данных
  experiments/          четыре сценария, вся содержательная работа здесь
  ui/                   интерфейс: один html, один js, один css, без сборки
docker-compose.yml      стек в собственной сети, наружу не смотрит
docker-compose.publish.yml  внешний маршрут; подключается только при публикации
scripts/
  fetch_corpora.py      сборка корпусов из законных источников
  prepare_build.sh      снимок исходников MagicBrain фиксированной ревизии
  run_scenarios.py      прогон всех сценариев через HTTP
  ab_delay_fix.py       сравнение «до/после» исправления линии задержек
  render_runs.py        сборка docs/RUNS.md из фактических файлов прогонов
tests/                  тесты честности оценки, происхождения данных и режима
data/corpora/           тексты и манифест с sha256 и классами данных
var/                    состояние: прогоны и модели (не в git)
```
